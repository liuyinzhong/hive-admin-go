# ADR 0004: 通知中心采用应用层自研组件,逐条消费菜单消息

日期: 2026-09-10
状态: 已接受

## 背景

布局右上角长期使用 Vben 上游的 Notification 演示组件,列表与交互全部是前端假数据。菜单消息体系落地后,消息只有菜单角标这一个聚合入口,持久化的标题、内容没有逐条展示位置。上游组件的契约(头像、清空、删除、查看全部)与菜单消息的领域语义(提醒、绑定菜单、进入即整组已读)不匹配,直接喂数据需要大量特判,且交互调整会触及公共包。

## 决策

1. **在应用层自研通知中心组件**(`src/layouts/components/notification-center.vue`),通过 BasicLayout 的 notification 插槽替换上游组件;不修改公共包,上游 Notification 组件不再被业务应用引用。
2. **列表契约**:当前用户全部来源、含已读、最近 100 条、按创建时间倒序;在弹层打开时拉取,打开期间不实时刷新,实时性由未读汇总推送承担(红点、菜单角标、提示音不变)。
3. **三种已读动作**:点击消息项 = 该菜单整组已读并跳转(与"进入菜单必整组已读"不变量一致,复用既有整组已读接口);消息项标为已读按钮 = 逐条已读,是系统内唯一单条已读路径;头部全部已读 = 全量已读。**不做删除/清空**——消息是提醒不是待办本体,旧消息靠"只取最近 100 条"自然沉出列表。
4. **红点规则**:铃铛红点亮起当且仅当未读总数大于 0,具体计数语义由菜单角标承担;消息项以来源菜单名标识归属,不使用上游组件的头像字段。

## 理由

- **自研 vs 复用上游组件**:上游契约的 avatar、clear、remove、viewAll 与领域语义冲突;自研后每个交互都有明确业务含义,且公共包零改动。
- **点击项整组已读 vs 逐条已读**:进入菜单必然整组已读是既有不变量,点击跳转若只读单条会造成"人已在菜单页、角标还在"的矛盾;逐条语义保留在标为已读按钮上,承担"不跳转、只想消掉这一条"的场景。
- **不删除**:删除对提醒类消息没有业务价值,却引入物理删除语义和误删未读提醒(角标丢失)的风险。

## 后果

- [SYS-MSG-001](../../business-docs/system/message-push.md) 的"菜单消息不是通用通知中心、不提供逐条消息列表"边界自本决策起反转:通知中心成为逐条消费入口,但"不是全量归档页"仍然成立。
- 修订 [ADR 0003](./0003-workflow-notice-via-menu-message.md) 决策 1 中"不接铃铛组件"的范围表述——那是流程提醒落地时的范围决策;通知中心落地后,流程待办与抄送通知自然进入通知中心,菜单角标机制不变。
- 消息仍无生命周期清理(SYS-MSG-009),通知中心列表以 100 条为窗口,更早消息只能经菜单角标进入对应页面消费。
