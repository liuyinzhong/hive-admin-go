# ADR 0002: 动作类型按启动类型分轨挂载,插入记录采用双值来源与三层校验

日期: 2026-09-09
状态: 已接受

## 背景

ADR 0001 建立了自动化动作机制,版本仅实现"修改字段值"(update_field),且规定手动发起流程禁止挂载一切动作。业务需要扩展第二类动作"插入记录"(insert_record):审批流转的某时机向目标业务表插入一条新记录(典型:功能开发审批通过后创建规划中需求,值取自审批表单)。

直接扩展遇到架构矛盾:插入记录的值来源依赖表单变量,而 ADR 0001 决定被动触发流程禁关联表单(WF-DEF-034)——能挂动作的流程没有表单,有表单的流程(手动发起)当时被禁止挂任何动作。若不调整,"值来源=表单字段"无处安放。

## 决策

1. **动作类型 × 启动类型分轨矩阵**取代"手动发起禁挂一切动作":修改字段值仅被动触发流程可挂(依赖业务流程绑定),插入记录仅手动发起流程可挂(值来源依赖表单变量)。两类动作互斥分属两轨,发布校验按矩阵拦截。
2. **插入记录的值来源仅两种**:固定值与表单字段。"来源业务对象字段"(如从需求字段复制到任务)明确推迟为演进项,避免一次性实现两套取值逻辑。
3. **插入目标即动作自身的业务类型**,不设独立目标业务类型配置(动作 businessType 一词两义:既是挂载过滤维度也是插入目标,避免两个同源下拉的冗余;放弃"需求流程插任务"类交叉场景,该场景语义混乱)。**可插字段目录**按业务类型在注册表声明(字段/中文名/必填标记/字典映射),目录外字段不可插入;目标业务必填字段在动作库保存时强制要求已配置映射(配置期拦截);固定值的字典值与引用字段在配置期做存在性校验。
4. **表单字段名弱引用三层校验**:动作库保存只校验非空(动作库是全局的,不知道哪个流程会用);设计器挂载时按当前流程绑定表单即时警告缺失(不阻断);发布校验硬拦截(字段不存在或流程未绑表单则拒绝发布)。
5. **插入的副作用**:同事务写入新记录、业务变更记录(行为=自动化动作)与业务流程绑定(新记录↔本审批实例);目标业务为需求时,审批事务提交成功后链式自动发起该需求的默认流程(与手工创建行为一致)。

## 理由

- **分轨而非重开"手动发起绑定业务对象"**:绑定业务对象发起方式已被 ADR 0001 定为被动匹配,重开会推翻默认流程机制;分轨让每类动作只依赖自己真正需要的上下文(绑定 vs 表单),矩阵校验在发布期拦截错配,比运行期报错前置。
- **值来源只做固定值+表单字段**:与首批场景(审批通过建需求)完全匹配;"业务对象字段"来源需要额外的字段映射界面与运行期取值路径,推迟不堵死(mappings 的 sourceType 枚举可扩展)。
- **配置期拦截必填**:插入的必填字段(如需求标题)缺失必然导致运行期失败,在动作库保存时拦截成本最低;表单字段名因动作库无流程上下文,只能后置到挂载警告+发布拦截,形成三层递进。
- **链式发起对齐手工创建**:插入的需求若不发起流程,会与手工创建行为分叉,产生"同是需求两种生命周期"的心智负担;复用默认流程匹配使入口无关、行为一致。

## 后果

- 手动发起流程现在可以挂动作了(仅插入记录),ADR 0001 中"手动发起流程禁止挂载修改字段值动作"的表述收窄为矩阵规则,由本 ADR 取代该子句。
- 插入记录挂载节点的选择完全自由(任意节点完成时执行),但重走路径会再次执行——插入动作每次产生新记录,重复退回审批会产生多条记录,这是已接受的行为(与"审批重新通过"业务语义一致)。
- 新增动作类型的成本清单:动作类型常量+参数结构+校验分派+执行分支+快照结构与前端参数区,画布协议与触发链路不变。
