# ADR 0001: 自动化动作采用发布时快照挂载,流程定义按启动类型双轨发起

日期: 2026-09-07
状态: 已接受

## 背景

工作流与业务数据的联动先后出现过三种形态:业务状态钩子(代码注册,按 business_type 路由回写已有对象状态,原"状态同步事件")、结束后落地创建(结束节点开关,流程通过后创建新需求)、以及业务对象创建后自动发起流程(按"最新发布"猜测目标定义)。三者机制分散、叫法不一,且自动发起的猜测规则在多定义并存时会误匹配甚至无限套娃。

重构目标:统一为一套配置化的「自动化动作」机制,消除猜测,支撑后续"插入记录"等动作类型扩展。

## 决策

1. **动作库与挂载分离,挂载采用发布时快照。** 动作配置是全局主数据存于 `wf_automation`(独立菜单维护);设计器按业务类型筛选动作,选中即把动作完整配置快照写入节点画布属性(`automations` 数组)。运行时实例只按快照执行,不回查动作库。
2. **流程定义按启动类型(startType)双轨。** 0 手动发起:纯流程,出现在申请入口,不绑定业务对象,发布校验禁止挂载修改字段值动作;1 被动触发:不出现在申请入口,必须由业务对象携带绑定发起,是自动化动作的承载方。发起服务双向拦截。
3. **自动发起显式化。** 业务对象(需求)创建后的自动发起改为"被动触发+默认流程标志(is_default)+业务类型+已发布"精确匹配,默认流程由管理员在定义列表显式设置、同类型唯一,废除"取最新发布"的猜测规则。
4. **业务类型值域统一为 BUSINESS_TYPE 字典值**(0需求/10任务/20缺陷/30版本),贯穿定义声明、动作库配置、绑定表与执行器定位,由后端业务类型注册表(`business_type_registry.go`)作为唯一映射来源;不兼容旧英文键("story"等),相关表数据清空重建。

## 理由

- **快照 vs 实时引用**:实时读取动作库会让已发布/运行中实例的行为随库变更漂移,且必须处理"ID 已删除"的运行期故障;快照与本项目既有哲学一致(实例保存定义/流程/表单快照,WF-RUN-003),动作库修改需重新挂载并重新发布才生效,语义单一。
- **双轨 vs 单轨+运行时校验**:若不区分启动类型,纯流程实例挂载业务对象动作只能在运行期报错(最后一个审批人承担失败);双轨把冲突在发布阶段结构性拦截,代价仅是定义上多一个必选属性。
- **显式默认 vs 猜测最新发布**:猜测规则在多定义并存时误匹配;"功能开发审批"类纯审批流程与"需求评审流程"同类型并存时,新需求可能自动发起错误流程甚至无限套娃。显式指定的管理成本(一次"设为默认"操作)远低于误匹配的排查成本。
- **字典值统一**:消除"story(英文键)/0(字典值)"双值域,注册表成为业务表映射、可写字段白名单、字典翻译的唯一来源,动作库与执行器不再各自维护映射。

## 后果

- 动作库修改/停用/删除对已挂载快照零影响;要更新已发布流程的动作配置,必须重新挂载并重新发布。
- 动作快照的校验依赖发布时刻的白名单;白名单收窄后,存量快照在执行期(而非发布期)被拒——可接受,收窄白名单属于破坏性变更。
- 新增业务类型必须同时登记后端注册表,字典加值不登记注册表时发布校验会拒绝("业务类型未注册"),配置面不会出现不可执行的类型。
- 后续扩展(insert_record 插入记录等)只需:动作类型枚举加值、action_config JSON 加结构、执行器加分支、表单加参数区,画布协议与触发链路不变。
