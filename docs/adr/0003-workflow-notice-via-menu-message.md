# ADR 0003: 流程待办与抄送提醒复用菜单消息体系,按任务与抄送记录确定性触发

日期: 2026-09-09
状态: 已接受

## 背景

流程流转到审批节点后,办理人只能主动进入"我的待办"才能发现新任务;抄送记录生成后接收人同样无未读感知。系统已有两套通知形态:右上角铃铛通知组件(仅前端演示数据,未接后端)与菜单未读消息体系(持久化 + 未读聚合 + SSE 推送,消费端角标、提示音、整组已读已完整落地,下载中心与需求流转通知已在使用)。

## 决策

1. **提醒复用菜单消息体系**,不新建通知中心、不接铃铛组件、不做逐条消息列表。待办提醒绑定菜单 `WorkflowTaskList`(我的待办),抄送提醒绑定菜单 `WorkflowCopyList`(我的抄送)——通知永远绑到它的消费入口。
2. **触发与引擎产物一一对应**:引擎每生成一条保持待办状态的审批任务,向该办理人发一条流程待办通知;每生成一条抄送记录,向该接收人发一条流程抄送通知。自动通过(与上一节点审批人相同)与或签已被取消的任务不发;拒绝、撤销、减签不产生提醒;转办、加签产生的新待办发提醒;不排除操作人本人。
3. **发送在流程事务提交后执行**,失败仅记日志,不回滚流转;发送复用 `CreateMenuMessageForMenuName` 内部能力,与链式自动发起需求的暂存-提交后执行模式一致。
4. **通知动作化留作将来扩展,本次不做**:自动化动作在节点完成时执行,彼时下一节点审批人尚未解析,动作模型表达不了"通知下一节点审批人";将来若做"节点完成时通知发起人/指定人/角色"类动作,复用同一发送服务与事务后执行通道,与内建规则并存——内建管"你有待办/被抄送",动作管"业务自定义知会"。

## 理由

- **菜单消息 vs 新通知中心**:菜单消息的持久化、聚合、推送与前端消费端均已落地并有先例;新通知中心要重建推送链路与组件,且系统没有逐条消息列表页,通用通知会出现"角标亮了没处看"的断头路。
- **确定性触发 vs 可配置动作**:待办提醒是引擎固有语义("生成待办即提醒"),无需按流程配置;动作化会引入收件人模型、文案模板、快照字段和"失败不回滚"的失败语义特例,而本次需求唯一的收件人"下一节点审批人"恰恰是动作模型在执行时机上无法表达的,最终仍需内建。
- **绑消费入口 vs 全部挤一个角标**:抄送人可能不是任何节点的审批人,把抄送提醒挤进"我的待办"会让不相干页面吃掉角标。

## 后果

- **菜单消息已读 ≠ 任务/抄送已读**(必须知晓的坑):点进"我的待办"清掉的是提醒消息,不代表任务被处理;点进"我的抄送"清掉的是提醒消息,不代表抄送记录已读;反之处理任务或阅读抄送记录也不会清角标。两套状态相互独立,文档与后续实现不得混同。
- 每条待办任务对应一条消息,不做同人去重;将来引入并行分支时同一人可能收到多条,行为仍正确。
- 单进程 SSE 广播(SYS-MSG-006)与消息无生命周期清理(SYS-MSG-009)的既有限制对流程提醒同样适用。
- 转办规则本身禁止转给自己,其提醒总是发给新办理人;发起人本人作为首节点办理人时会收到自己发起流程的提醒,属预期行为。
