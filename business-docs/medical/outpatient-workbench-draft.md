# 医生接诊与处方规则

> 状态：首期已实现。本文记录医生叫号、门诊病历、疾病诊断档案、普通处方和处方审核的当前规则。

## 需求范围

首期围绕三个需求点设计：医生叫号、医生接诊、医生开处方。

## 已确认边界

### 医生身份

- 系统用户与医生档案分开创建，医生档案可关联系统用户。
- 一个未删除医生档案所绑定的系统用户，不能再绑定其他未删除医生档案。
- 现有 Service 已校验上述规则；后续实现需增加仅对未删除绑定生效的数据库唯一约束，防止并发写入突破校验。
- 医生档案删除或主动解绑后，原系统用户可以重新绑定。
- 叫号和接诊操作既要求对应权限码，也要求当前系统用户关联的医生就是该排班医生；后者属于业务归属校验，不是职位或人员授权。

### 候诊与叫号

- 候诊状态规划为：`0 候诊中`、`10 已叫号`、`15 已过号`、`20 接诊中`、`30 已完成`。
- 首次叫号：`0 → 10`；重复叫号：`10 → 10`；过号：`10 → 15`；重新叫号：`15 → 10`；开始接诊：`10 → 20`；完成接诊：`20 → 30`。
- 每次有效叫号都使 `call_count + 1`。首期不增加独立叫号日志，也不保存每一次叫号时间。
- 过号保留原签到序号，不重新排号，不修改挂号单状态，也不释放号源。
- 过号患者必须先重新叫号，不能直接开始接诊；首期不限制过号和重新叫号次数。
- 同一实际排班严格串行：同一时间最多只能有一名患者处于“已叫号”或“接诊中”。当前患者完成接诊或被标记为过号后，才能继续叫号。
- 普通“叫下一位”只能选择该排班中 `queue_status=0` 且 `queue_sequence` 最小的患者，医生不能跳号选择其他候诊患者。
- 已过号患者不参与普通“叫下一位”，由医生对指定患者执行“重新叫号”，并继续受严格串行约束。
- “过号”不等于挂号单的“爽约”：过号发生在签到并被叫号之后，爽约指已支付但未签到。

### 门诊病历

- “就诊记录”正式命名为“门诊病历”。一条挂号单最多对应一份门诊病历。
- “患者病历”是按患者汇总历次门诊病历、诊断和处方的长期视图，首期不单独建表。
- 开始接诊时，挂号单保持 `30 已签到`，候诊记录由 `10 已叫号` 更新为 `20 接诊中`，并创建门诊病历、记录开始接诊时间。
- 门诊病历不维护状态枚举。是否接诊中、是否完成以候诊记录状态为准。
- 接诊中允许持续保存和修改门诊病历、开处方；完成后门诊病历只读，处方仅在药师审核不通过时允许原医生修改后重新提交。首期不支持重新接诊或撤销完成。
- 完成接诊时，在同一事务内将候诊记录由 `20 → 30`、挂号单由 `30 → 50`，并记录门诊病历完成时间；任一步失败整体回滚。
- 门诊病历采用通用固定字段，首期不做动态专科病历模板。

医生可填写的通用字段：

| 分组 | 字段 |
|---|---|
| 就诊信息 | 初诊/复诊、病史陈述者 |
| 生命体征 | 体温、脉搏、呼吸频率、收缩压、舒张压、身高、体重 |
| 病史 | 主诉、现病史、既往史、个人史、家族史、过敏史、婚育史、月经史 |
| 检查 | 体格检查、专科检查、辅助检查结果 |
| 诊断 | 主要诊断、其他诊断 |
| 诊疗 | 处理方案、医嘱、复诊建议、备注 |

接诊过程中允许保存不完整病历；完成接诊时必须校验初诊/复诊、主诉、现病史、主要诊断和处理方案。

- 门诊病历不单独生成业务编号，使用 UUID 作为主键；本次就诊使用挂号单号展示和检索，患者长期维度使用患者编号。
- 门诊病历保存唯一的 `registration_id`，并保存便于业务查询的 `patient_id`、`doctor_id`、`department_id`；姓名、科室名称和挂号单号等展示信息使用挂号单已有快照，不重复保存。
- 完成接诊使用独立接口 `POST /api/medical/outpatientRecords/{recordId}/complete`，不复用挂号管理动作。
- 挂号管理当前不再提供调试“完成接诊”按钮、接口或 `medical:registration:complete` 权限码；后续不得重新加入绕过正式接诊校验的入口。
- 当前排班医生开始接诊后，可以只读查看患者历次已完成门诊病历和关联处方，包括其他医生和科室的历史记录；开始接诊前不能提前浏览。

门诊病历使用 `med_outpatient_record`，不维护状态、删除标记和乐观锁版本。保存时以后一次请求为准。`registration_id` 必须唯一。

门诊病历诊断使用 `med_outpatient_diagnosis`，保存疾病诊断档案关联及 ICD 编码、名称快照；同一病历不能重复选择同一诊断，最多一条主要诊断，完成接诊时校验至少一条主要诊断。

### 疾病诊断档案

疾病诊断主数据的权威规则见 [疾病诊断档案规则](./diagnosis.md)。本模块只补充接诊上下文：医生从启用档案选择诊断，病历明细保存档案关联及 ICD 编码、名称快照；同一病历不能重复选择同一诊断，完成接诊时必须且只能有一条主要诊断。

### 处方

- 处方不是完成接诊的必填条件，没有处方也允许完成接诊。
- 一份门诊病历可以关联多张处方，每张处方拥有独立处方编号和多条药品明细。
- 每张处方归属于当前门诊病历和当前接诊医生。
- 首期只支持西药和中成药使用的普通处方，不支持需要剂数、煎法、服法等专用结构的中药饮片处方。
- `prescription_type` 使用 `10 普通处方、20 中药饮片处方`；首期只允许创建 `10`，`20` 仅为后续扩展预留。
- 处方编号使用 `base_code_sequence` 全局递增生成，不拼接日期，前缀为 `RX`。审核不通过后修改并重新提交仍使用原编号。
- 开方药品直接引用现有产品档案中 `DRUG` 类型的 SKU，不再建设独立药品档案；新选择要求 SPU、RP、MP、SKU 全链路均启用且未删除。
- 处方明细保存 `sku_id`，并快照保存药品名称、规格、剂型、生产企业、批准文号和包装单位等关键信息。
- 每条明细包含单次用量、给药途径、用药频次、疗程天数、最终发药数量和单位、用药说明及备注。
- 同一张处方不能重复选择同一个 SKU；复杂或分阶段用法首期写入用药说明。
- 提交处方时必须至少有一条明细，并重新校验产品全链路及明细完整性；不校验库存。提交后的产品档案变化不影响处方快照。
- 处方提交时固化门诊病历当时的全部诊断明细快照；审核不通过后重新提交时刷新诊断快照。

### 用药数量计算

- 单次用量必须使用 SKU 最小单位，例如粒、片、毫升；首期不解析产品档案中的含量文本。
- 给药途径使用 `MED_MEDICATION_ROUTE` 字典。
- 用药频次使用前后端统一枚举，不使用可任意新增的普通字典。
- 首期频次包括：每日一次、每日两次、每日三次、每日四次、每晨一次、每晚一次、每 8 小时一次、每 12 小时一次、隔日一次、每周一次、立即一次、必要时和需要时。
- 除“必要时、需要时”外，系统根据单次用量、频次和疗程自动计算最终发药数量，医生不能手工覆盖；不可计算频次由医生填写最终发药数量。
- 允许拆零时按 SKU 最小单位保存实际数量，并按包装换算展示，例如 `1盒18粒（共42粒）`；不允许拆零时向上取整为整数包装数量，不显示小数盒。
- 单次用量和最小单位总量最多保存三位小数，以支持半片、口服液和儿童小剂量等场景；页面去除末尾无效零。首期不校验药片本身是否允许掰开。

### 处方审核

- 所有普通处方都必须经过药师审核，通过后才能进入未来的发药流程。
- 处方状态为：`0 草稿`、`10 待审核`、`20 审核通过`、`30 审核不通过`、`40 已作废`。
- 医生可以提交草稿 `0 → 10`、作废草稿 `0 → 40`，也可以在尚未产生审核结果时撤回 `10 → 0`；撤回和审核通过事务锁互斥。
- 审核人可以执行 `10 → 20` 或 `10 → 30`。审核不通过后，原医生可以修改并重新提交 `30 → 10`；也可以将草稿或审核不通过处方作废。
- `20 审核通过`和`40 已作废`为本期终态。由于本期不管理发药，审核通过后不能修改或作废。
- 完成接诊不等待药师审核，`10 待审核`允许完成；处方处于草稿或审核不通过时，必须提交或作废后才能完成接诊。
- 审核页面和审核动作统一按 `medical:prescriptionReview:access` 权限码判断，不依赖职位或人员类型；审核人不得审核自己开具的处方。
- 审核通过时意见选填，审核不通过时意见必填。每次审核独立记录审核人系统用户 ID、结果、意见和时间，不覆盖历史审核记录。
- 处方使用“当前处方 + 每次提交快照”结构，当前数据与历史审核内容互不覆盖：
  - `med_prescription`：当前处方头及状态；
  - `med_prescription_item`：医生当前编辑的药品明细；
  - `med_prescription_submission`：每次提交版本及对应审核结果；
  - `med_prescription_submission_item`：提交时药品明细快照；
  - `med_prescription_submission_diagnosis`：提交时诊断快照。
- 第二版审核通过时只更新处方当前状态，不从提交快照反向覆盖当前主表和明细表；待审核期间禁止医生修改当前明细。
- 提交快照同时固化审核所需的过敏史等关键临床信息，确保可以还原药师当时看到的内容。

### 本期下游边界

- 处方单不等于发药单；发药单是未来药房实际履约和库存扣减的业务凭证。
- 本期不建设发药单、销售出库、库存扣减、药品批次、追溯码、收费和退药流程。
- 普通处方和未来的中药饮片处方统一使用处方列表和详情查询，通过 `prescription_type` 区分；创建和修改接口可以按类型拆分。
- 中药饮片处方未来复用处方头、提交版本和审核流程，并增加中药专用扩展表。
- 治疗执行单和检查申请单不是药品处方，未来分别建设并关联门诊病历，不进入处方查询接口。

### 页面和数据范围

- 首期新增三个入口：医生工作台、处方审核、疾病诊断档案。
- 不单独增加门诊病历管理和处方管理页面，历史内容首期从医生工作台对应患者进入查看。
- 当前系统用户必须绑定启用医生档案才能进入医生工作台；工作台只查询当前医生自己的排班，不能选择其他医生。
- 工作台只展示当天已发布且未停诊的排班，首期不提供任意日期切换。
- 当天排班不限制当前时间是否落在排班开始和结束时间内；患者签到进入队列后即可提前叫号，超过结束时间也可继续完成剩余接诊。
- 开始接诊后不提供撤销接诊，只能填写病历并完成接诊。
- 候诊队列始终脱敏；医生进入自己排班患者的接诊页面后，患者信息不脱敏，也不额外要求 `medical:patient:viewSensitive`。
- 医生工作台和门诊病历响应中的集合字段始终返回数组；`queues`、`diagnoses`、`prescriptions`、处方 `items` 及提交快照没有数据时返回空数组 `[]`，不返回 `null`。
- 医生工作台采用完整页面：左侧展示当天排班和候诊队列，中间展示当前患者和门诊病历，下方或右侧展示诊断与处方；处方编辑可以使用抽屉。
- 首期沿用上述工作台布局，不按 ABC 诊所管家的三栏界面调整；ABC 的布局与交互仅作为后续版本的可选参考。
- 门诊病历使用文档式结构化录入：固定文书中保留可点击占位，点击后在原位置切换为输入控件；后端仍按独立字段保存，不保存整段 HTML 或富文本。
- 病历字段失焦后延迟自动保存，页面展示保存状态；完成接诊前强制保存一次并执行后端校验。

### 权限边界

- 医生工作台及其中全部接诊动作共用 `medical:doctorWorkbench:access`，按钮是否可操作只由业务状态决定。
- 处方审核页面及审核动作共用 `medical:prescriptionReview:access`。
- 疾病诊断档案使用 `medical:diagnosis:list`、`create`、`detail`、`update`、`status`、`delete`。
- 权限码之外，医生工作台接口始终校验当前系统用户绑定启用医生档案且为当前排班医生；处方审核始终校验不能审核本人处方。
- 通用角色部门数据范围不扩大医生工作台、门诊病历、处方或审核对象；`all` 也不能替代当前排班医生、原开方医生、流程状态和不得自审等领域归属校验。

### 疾病诊断档案录入

- 首期只提供页面单条新增和修改，不提供 Excel 导入；批量导入以后再做。

## 迁移、兼容性与回滚

- 迁移新增八张业务表、处方编号公共流水，并为医生绑定用户增加仅未删除记录生效的唯一约束。
- 添加医生用户唯一约束前应先检查存量未删除医生是否重复绑定同一系统用户；存在重复时迁移会失败，需人工处理后重试。
- 回滚应用时先停止医生工作台写入并恢复旧版前后端。只有确认新增门诊病历和处方数据可以丢弃后，才可人工删除新增表和唯一约束；删除操作不可恢复。
