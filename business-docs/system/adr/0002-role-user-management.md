# 角色用户管理：从严数据权限档、增量接口与物理删除关联

角色与用户的授权关联此前只能通过用户编辑接口以全量 `roleIds` 集合间接维护。现新增角色维度的角色用户管理接口（`GET/POST/DELETE /system/roles/{roleId}/users`），并做三项边界决策。词汇沿用 `sys_user_role`、`dev_project_user` 和权限码 `system:role:user` 的既有 "user" 用词，不引入 "member" 同义词。

1. **数据权限档位**：角色用户的添加与移除与角色创建、更新、启停、删除同档，要求操作者为全部数据范围（`requireAllDataPermission`）；角色用户查询只要求 `system:role:detail` 原子权限码，不要求全部范围。理由：向一批用户批量授权影响面大，与角色管理页其它写操作的权限模型保持一致；科室级自助授权仍可走用户管理入口（`validateManagedRoles`），能力不丢失。
2. **增量接口**：按"添加用户 / 移除用户"设计，不做全量替换，重复添加与重复移除均幂等跳过。理由：一个角色的用户可达上千人，全量回显与提交存在性能和并发覆盖问题；项目用户的全量模式（上限 50 人）不适用于该量级。
3. **关联表物理删除**：`sys_user_role` 定性为纯关系表，用户移除、删除角色清理、删除用户清理、用户编辑重建统一使用物理 DELETE，`del_flag` 列保留但恒为 0；新增唯一键 `uk_sys_user_role_role_user(role_id, user_id)`，兼做按角色查用户的覆盖索引与并发防重。理由：原软删与物理删混用导致历史行堆积且无法建立唯一约束。

## Considered Options

- 数据权限用"用户管理档"（`validateManagedRoles` + 部门范围校验）：科室自助更便利，但批量授权下校验语义复杂，且与角色配置类操作档位不一致，放弃。
- 全量替换接口（对齐项目用户 `PUT /dev/project-users`）：用户量级大时不可用且并发互相覆盖，放弃。
- 维持软删 + `(user_id, role_id, del_flag)` 组合唯一键：同一对关系多次删除会产生多条 `del_flag=1` 行撞键，问题不根治，放弃。
