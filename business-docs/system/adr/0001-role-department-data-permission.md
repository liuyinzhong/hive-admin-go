# ADR-0001：角色与部门数据权限

- 状态：已采用
- 日期：2026-08-13

## 背景

系统已有 Bearer Token 和原子接口权限，但多数业务表只靠接口门禁，知道记录 ID 的用户可能绕过列表直接访问详情或写接口。现有数据普遍保存创建人/办理人，并已有系统用户、角色和组织部门关系；项目没有仓库、医疗机构等专用授权维度。

## 决定

采用“角色声明范围、请求时合并、Service 在业务查询上过滤”的模型：

1. 角色范围支持全部、自定义部门、本部门、本部门及下级、仅本人和无数据；多角色取并集。
2. 部门范围把业务记录的归属用户映射到该用户当前有效部门，不在每个业务表复制部门快照。
3. 列表、详情、写入、批量动作、统计和异步导出共用同一范围语义并默认关闭访问。
4. 全局主数据保持全局，由原子权限控制；流程、医生工作台等已有明确参与者边界的资源继续使用领域归属。
5. 异步任务执行时重新解析当前授权，避免权限撤销后仍按旧快照导出。

## 取舍

- 当前部门关系能立即反映调岗，运维简单；代价是历史记录的可见范围随人员部门变化，而不是创建时部门快照。
- 复用归属用户字段能覆盖现有项目且无需大规模改表；代价是空归属历史数据必须关闭访问，少数未来领域可能需要独立授权维度。
- Service 显式应用范围便于按业务对象选择归属字段；代价是每个新增路由必须完成分类审查，不能依赖一个全局 GORM 回调自动猜测。
- 全局主数据不按创建人切分能保持产品、仓库、字典等引用一致；因此管理员必须同时谨慎配置原子权限，不能把 `none` 误解为禁止所有全局配置动作。

## 后果

新增或修改接口必须先归类为公开、角色数据范围、当前用户归属、来源继承、领域归属或全局主数据，并在业务文档中登记。若现有归属字段无法表达真实边界，应先设计新的授权维度或归属关系，不能把数据权限省略为“以后再做”。
