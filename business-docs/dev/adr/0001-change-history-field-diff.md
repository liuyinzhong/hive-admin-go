# ADR 0001: 变更记录增加字段级明细,结构化存储于单列 JSON

日期: 2026-09-18
状态: 已接受

## 背景

开发管理的需求、任务、缺陷变更记录此前只记录行为类型(创建/修改/流转/确认/自动化动作)与富文本正文。修改类操作(整体修改、局部字段修改)正文为空,无法回答"改了哪个字段、从什么值改成什么值";流转与自动化的值变化只拼在富文本正文里,非结构化,前端无法稳定展示。

## 决策

1. `dev_change_history` 新增 `change_items` 列(text),存 JSON 数组,每项为 `{fieldKey, fieldLabel, dictType, oldValue, newValue}`。不建明细表,不借用 `extend_json`(明细是核心内容而非扩展;查询只有"按 businessId 查时间线"一种,明细表是过度设计)。
2. 值的翻译策略:字典值存原始值并携带 `dictType`,由前端复用字典翻译展示(字典改名后历史展示自动跟进);引用值(人名、版本名、模块名、文件名)与字段标签 `fieldLabel` 由后端在写入时翻译为可读文本固化(与现有变更正文中文固化行为一致)。
3. 覆盖范围:整体修改、局部字段修改、流转(状态 from→to)、缺陷确认、工作流自动化修改字段值五类动作生成明细;创建、删除、评论、自动化插入记录保持现状。富文本描述字段只记一条"描述已更新",不做内容级 diff;附件字段记增删文件名。
4. 存量记录不迁移,`change_items` 为空时前端按原有样式降级展示。

## 理由

- 单列 JSON 对比明细表:变更日志无按字段过滤、无跨记录聚合查询,单列即可承载,避免 join 与迁移成本。
- 对比拼进富文本正文:正文是自由格式,无法保证结构稳定,前端只能 v-html 整段渲染。
- 字典值前端翻译、引用值后端固化是混合策略:字典是全局受控词汇适合动态翻译;人名等引用值在写入时刻才有可靠的翻译上下文。

## 后果

- 整体修改、局部修改、流转、确认的写入路径需先读旧值再更新,diff 在同一事务内计算,单条主键查询成本可接受。
- 历史记录中引用值文本是写入时刻的快照,后续对象改名不会回溯历史(与字典值动态翻译不同),这是接受的语义差异。
